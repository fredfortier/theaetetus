# Specification: `invariant-formulation`

Status: implemented.

## Intent and boundary

Provide a reusable operation for converting an already-owned causal account into compact system
truths. The skill does not discover requirements, supply missing intent, select architecture, or
authorize implementation.

## Naming decision

`invariant-formulation` names the output concept and the operation without preserving an imperative
source phrase. It is distinguishable from `specification-development`, which owns the larger
argument, and `conformance-review`, which judges realized correspondence.

## Required behavior

1. Bind every invariant to an owned premise and governed subject.
2. Use `evidence-grounding` when the premise depends on factual or external support.
3. Express valid behavior positively and expose its illegal negation once.
4. Name enforcement and verification boundaries.
5. Reject task-shaped, symptom-shaped, file-shaped, and prose-dependent candidates.
6. Compress overlap without weakening meaning.
7. Return missing premises rather than inventing intent.

## Invariants

- A retained invariant survives valid implementation refactoring.
- Its responsible boundary can enforce it and its verification observation can discriminate it.
- An exclusion follows from a positive property or a demonstrated drift path.
- The skill never turns a candidate invariant into implementation authority.

## Shape and precision

Class: focused reasoning utility. Primary shape: inline guidance. A reference, script, template, or
router would add indirection without serving a conditional lookup or deterministic operation.

The port retains positive properties, illegal negation, boundary ownership, verification, and
compression. It removes source-specific routes, roles, repository labels, and the implication that
invariant formulation is a mandatory lifecycle phase.

## Validation cases

- A blacklist of components becomes one boundary-bearing valid-state property.
- A filename guardrail is rejected as implementation-shaped.
- A lifecycle property identifies both its transition owner and observable check.
- An unowned failure semantic returns a missing premise instead of a plausible invariant.
